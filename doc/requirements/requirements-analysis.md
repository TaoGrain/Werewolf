# 多 Agent 狼人杀需求分析

## 1. 文档信息

- 文档状态：需求分析初稿
- 当前版本：0.4
- 更新日期：2026-07-20
- 适用范围：多 Agent 狼人杀 MVP 及后续扩展

## 2. 项目背景

本项目希望构建一个由大语言模型 Agent 扮演全部玩家的狼人杀游戏。用户不直接扮演普通玩家，而是作为主持人或观察者创建游戏、开始游戏、控制阶段推进、查看游戏过程，并在游戏结束后复盘整局表现。

系统需要模拟真人狼人杀的核心体验：每名 Agent 拥有独立身份和有限信息，根据自己掌握的公开信息、私有信息和历史记忆进行发言、推理、夜间行动及投票。Agent 投票时必须给出可展示的游戏内理由。

## 3. 项目目标

### 3.1 核心目标

1. 支持一局完全由 Agent 参与的基础狼人杀游戏。
2. 由系统严格控制发牌、阶段切换、行动合法性、死亡结算和胜负判断。
3. 保证不同 Agent 之间的身份、私有信息和私有记忆相互隔离。
4. 让 Agent 能够根据历史发言和投票形成持续变化的判断。
5. 保存每次 Agent 与 LLM 的实际交互，用于游戏中调试和赛后复盘。
6. 允许用户手动控制游戏推进，观察每个阶段的执行结果。
7. 提供基于事实记录的完整对局回放和 Agent 决策复盘。

### 3.2 非目标

以下内容不作为第一版的必要目标：

- 真人玩家与 Agent 混合参与。
- 实时语音、语音识别或语音合成。
- 警长竞选和复杂警徽流。
- 狼人自爆、守卫、猎人、白痴、情侣及第三方阵营等扩展机制。
- 多服务器分布式 Agent。
- 3D 场景或高复杂度游戏动画。
- Agent 自由修改游戏规则或直接操作游戏数据库。

## 4. 参与者与权限

### 4.1 用户

用户在第一版中承担主持人和观察者角色，可以：

- 创建和配置游戏。
- 开始游戏。
- 控制进入下一阶段。
- 暂停游戏。
- 在失败时重试当前阶段。
- 查看公共对局信息。
- 根据查看模式检查 Agent 私有上下文。
- 游戏结束后查看全部身份和完整复盘。

用户是否需要在后续版本中扮演普通玩家，暂不纳入 MVP。

### 4.2 Agent 玩家

每名 Agent 玩家具有：

- 唯一玩家编号和座位号。
- 独立角色身份。
- 独立人格配置。
- 独立对话上下文。
- 独立私有记忆和判断。
- 当前阶段允许执行的有限行动。

Agent 无权：

- 直接读取完整游戏状态。
- 读取其他玩家私有记忆。
- 读取不属于自身视野的身份和夜间信息。
- 决定游戏阶段如何切换。
- 直接修改死亡状态、药物数量或胜负结果。

## 5. 基础游戏规则

### 5.1 MVP 建议配置

第一版建议先支持 6 人局：

- 2 名狼人。
- 1 名预言家。
- 1 名女巫。
- 2 名平民。

角色数量应通过规则配置保存，后续可以扩展到常见 9 人局。

### 5.2 身份认知

- 每名玩家知道自己的身份。
- 平民不知道其他玩家身份。
- 狼人按照标准规则知道狼队友身份。
- 预言家只知道自己的身份和已经完成的查验结果。
- 女巫知道自己的身份、药物剩余情况以及规则允许获知的当晚刀口。
- 死亡玩家不能继续参与后续发言、夜间行动和投票。

### 5.3 胜负条件

建议采用以下基础条件：

- 所有狼人死亡，好人阵营获胜。
- 存活狼人人数大于或等于存活好人人数，狼人阵营获胜。

是否采用“屠边规则”需要在开发前确认，MVP 默认不采用。

## 6. 游戏流程需求

### 6.1 创建游戏

用户能够：

- 选择玩家数量和角色配置。
- 选择是否显示上帝视角。
- 选择游戏中是否允许查看 Agent 私密信息。
- 配置随机种子，或由系统生成随机种子。
- 创建一局尚未开始的游戏。

### 6.2 发放身份

用户点击开始后，系统必须：

1. 按规则随机分配身份。
2. 将身份写入受保护的角色分配数据。
3. 为每个玩家创建独立 Agent 会话。
4. 为每个 Agent 初始化人格和私有记忆。
5. 只向对应 Agent 提供规则允许的身份信息。
6. 记录随机种子、规则版本和发牌结果，供赛后审计。

### 6.3 夜间流程

基础夜间流程建议为：

1. 预言家选择查验目标。
2. 系统将查验结果写入预言家私有信息。
3. 两名存活狼人按座位号进行一轮私有讨论。
4. 讨论阶段完成后暂停推进，等待主持人再次点击下一阶段。
5. 狼人分别秘密提交最终击杀目标。
6. 系统确定狼人最终目标。
7. 女巫根据刀口和药物状态选择行动。
8. 系统统一结算当夜行动。
9. 系统检查胜负条件。

夜间行动和讨论不能出现在公共对话中。

### 6.4 白天流程

基础白天流程建议为：

1. 系统公布夜间公开结果。
2. 存活玩家按照座位顺序依次发言。
3. 后发言玩家可以看到此前已经公开的发言。
4. 发言结束后，所有存活 Agent 基于同一份冻结的公共状态提交投票。
5. 每张投票必须包含目标和公开理由。
6. 所有投票提交完成后统一公开。
7. 系统处理平票规则并执行放逐结算。
8. 系统检查胜负条件。

### 6.5 用户控制推进

系统必须支持用户手动触发以下操作：

- 开始游戏。
- 进入夜晚。
- 执行或完成当前夜间阶段。
- 开始白天发言。
- 开始投票。
- 结算投票。
- 进入下一天或下一夜。
- 暂停游戏。
- 重试失败阶段。

阶段执行中应禁用重复推进。重复请求不能造成重复用药、重复死亡或重复投票。

## 7. 游戏状态机

系统应至少包含以下状态：

```text
LOBBY
ROLE_ASSIGNED
NIGHT_SEER
NIGHT_WOLF_DISCUSSION
NIGHT_WOLF
NIGHT_WITCH
NIGHT_RESOLUTION
DAY_ANNOUNCEMENT
DAY_DISCUSSION
DAY_VOTING
DAY_RESOLUTION
FINISHED
```

游戏规则引擎负责判断允许的状态转换。LLM 只能返回行动意图，不能决定状态转换。

## 8. Agent 行为需求

### 8.1 独立人格

每名 Agent 可以具有不同的人格参数，例如：

- 发言风格。
- 激进程度。
- 风险偏好。
- 信任倾向。
- 欺骗倾向。
- 逻辑分析倾向。

人格应在单局游戏中保持稳定，避免所有 Agent 使用完全相同的语言风格。

### 8.2 独立记忆

Agent 需要记住：

- 已公开的发言。
- 已公开的投票和投票理由。
- 已公开的死亡信息。
- 自己掌握的私有信息。
- 自己对其他玩家的怀疑和信任变化。
- 自己过去已经做出的声明和行为。

Agent 不应记住其从未被允许看到的信息。

### 8.3 结构化输出

不同阶段应要求 Agent 返回可校验的结构化结果。

白天发言至少包含：

- 公开发言内容。
- 可展示的公开推理理由。
- 私有怀疑列表或策略摘要。

投票至少包含：

- 目标玩家。
- 公开投票理由。
- 可选的置信度。

夜间行动至少包含：

- 行动类型。
- 目标玩家。
- 私有行动理由。

系统不要求也不保存模型隐藏思维链，只保存模型实际输入、实际输出以及专门生成的可解释理由和策略摘要。

MVP 使用 MiniMax M3。由于 MiniMax M3 当前不能依赖服务端 `json_schema` 强制结构化输出，系统应通过提示词要求只返回 JSON，并在本地使用 Pydantic 完成解析和业务校验。解析失败时允许执行有限次数的格式修复或重新生成。

### 8.4 输出验证

系统必须校验：

- 目标玩家是否存在。
- 目标玩家是否存活。
- 当前角色是否有权执行该行动。
- 是否允许选择自己。
- 药物或技能是否仍然可用。
- 投票目标是否符合当前规则。
- 返回数据是否符合定义的结构。

无效输出允许自动重试；超过重试次数后，应将当前阶段标记为失败并允许用户重试，不能静默篡改 Agent 决策。

## 9. 信息隔离需求

### 9.1 玩家视图

每次调用 Agent 前，后端必须构造该玩家专属的玩家视图。不能将完整游戏对象传给 LLM 后再要求模型忽略秘密信息。

玩家视图至少分为：

- 公共游戏信息。
- 角色允许看到的私有信息。
- 当前 Agent 的私有记忆。
- 当前阶段允许的行动。

### 9.2 独立会话

每个 Agent 在每局游戏中必须使用独立会话标识，例如：

```text
game:{game_id}:player:{player_id}
```

不同 Agent 之间不能共享完整消息历史。

MiniMax 文本生成接口按请求接收消息历史，因此每个 Agent 的上下文由本系统在 SQLite 中独立维护。调用模型时只装载当前玩家允许看到的消息和记忆，不能依赖模型提供方替系统管理会话隔离。

### 9.3 信息可见级别

建议支持以下可见级别：

```text
PUBLIC
PLAYER_PRIVATE
WOLF_TEAM_PRIVATE
HOST_PRIVATE
POST_GAME_PUBLIC
```

前端隐藏不能替代服务端鉴权和过滤。服务端必须根据游戏状态和用户查看模式决定可以返回哪些内容。

## 10. LLM 对话记录需求

### 10.1 保存范围

每次 Agent 调用 LLM 时，必须保存：

- 游戏 ID、玩家 ID 和 Agent 会话 ID。
- 游戏天数和阶段。
- 调用类型和重试次数。
- 模型提供方和模型名称。
- MiniMax 请求 ID、响应状态和敏感内容检测标记。
- 提示词、规则、人格和输出结构版本。
- 实际发送给模型的全部消息快照。
- Agent 当时的公共视图和私有视图。
- 调用前的私有记忆快照。
- 模型响应中用于审计的原始业务字段和经过安全过滤的最终文本。
- `reasoning_content` 等内部推理内容不进入游戏记录、复盘界面或其他 Agent 上下文；只记录推理 token 数量等用量元数据。
- 解析后的结构化结果。
- 校验错误和重试信息。
- 输入、输出 token 数量。
- 开始时间、结束时间和调用延迟。
- 调用状态和错误信息。

### 10.2 不可变快照

调用记录必须保存当时实际发送的请求快照，不能在复盘时根据当前规则重新拼接。修改提示词或规则后，不得改变历史调用内容。

### 10.3 事件关联

每条由 Agent 产生的游戏事件应能够关联到对应 LLM 调用，例如：

- 一条公开发言关联到发言调用。
- 一张投票关联到投票调用。
- 一次夜间行动关联到夜间决策调用。

## 11. 游戏中查看 Agent 对话

用户点击某个玩家后，应能够打开 Agent 检查器，查看：

- Agent 事件时间线。
- 当前身份和角色信息，前提是已开启上帝视角。
- 每次 LLM 调用的分类展示。
- 实际请求和原始响应。
- 当前私有记忆。
- 对其他玩家的怀疑变化。
- 已执行的行动。
- token、延迟和错误信息。

Agent 检查器建议提供：

- 可读模式：按规则、身份、公共历史、私有历史、当前任务和响应分类。
- 原始模式：查看实际请求和响应 JSON。

如果查看内容包含尚未公开的身份或夜间信息，界面必须明确提示当前处于上帝或调试视角。

## 12. 赛后复盘需求

### 12.1 全局时间线

游戏结束后，应按照真实发生顺序展示：

- 身份分配。
- 狼人讨论及击杀决策。
- 预言家查验。
- 女巫行动。
- 夜间结算。
- 白天发言。
- 所有投票和理由。
- 死亡、放逐和胜负结算。

### 12.2 单 Agent 视角

用户可以选择一名 Agent，查看其在各时间点：

- 当时知道哪些信息。
- 当时看到了哪些发言和事件。
- 对每名玩家的判断如何变化。
- 为什么做出某次发言、投票或夜间行动。
- 是否疑似使用了不应知道的信息。

### 12.3 上帝视角对比

复盘应支持将真实身份与 Agent 判断进行对比，并能够展示：

- 好人识狼准确率。
- 狼人伪装效果。
- 投票命中率。
- 跟票和改票情况。
- 无效行动次数。
- 疑似身份泄漏次数。
- 每名 Agent 的 token 消耗和响应时间。

### 12.4 AI 复盘报告

后续版本可以增加独立的复盘 Agent，根据完整事实记录生成：

- 对局摘要。
- 关键转折点。
- 表现最佳玩家。
- 主要错误。
- 阵营策略评价。

AI 复盘报告必须明确标记为模型生成内容，不能替代原始游戏事件记录。

## 13. 数据需求

系统至少需要持久化以下实体：

- Game：游戏配置、状态、当前阶段、天数、规则版本、随机种子。
- Player：座位、名称、存活状态和人格配置。
- RoleAssignment：玩家身份和角色私有状态。
- GameEvent：追加式游戏事件。
- AgentSession：某玩家在某局游戏中的独立 Agent 会话。
- LLMCall：一次完整模型调用。
- LLMMessage：模型调用中的逐条消息。
- AgentMemorySnapshot：Agent 私有记忆快照。
- PhaseAction：阶段行动及合法性校验结果。
- Vote：投票目标、理由和结果。

历史事件和 LLM 调用记录应以追加为主，不应被后续流程覆盖。

## 14. 非功能需求

### 14.1 一致性

- 一个阶段只能成功结算一次。
- 重复请求不得产生重复副作用。
- 多个 Agent 并发完成行动后，结算顺序必须由规则引擎确定。
- 服务异常后不能出现药物已消耗但事件未记录的部分状态。

### 14.2 可恢复性

- 游戏状态必须持久化，服务重启后能够继续。
- 失败阶段应保留已完成的调用和错误记录。
- 用户可以在明确边界内重试失败阶段。

### 14.3 可测试性

- 游戏规则引擎应能在不调用真实 LLM 的情况下测试。
- 应支持使用模拟 Agent 返回固定行动。
- 应覆盖身份隔离、状态转换、夜间结算、投票和平票、胜负判断等测试。
- 应提供自动化测试检测某个 Agent 视图中是否意外包含其他角色私有信息。

### 14.4 可观测性

- 能查看每次 LLM 调用状态、耗时和 token。
- 能通过游戏 ID、玩家 ID、阶段和调用类型检索记录。
- 能定位结构化输出失败和重试原因。
- 应区分应用日志与包含身份信息的私密调试数据。

### 14.5 性能

- 白天依次发言可以串行执行。
- 基于同一冻结状态的投票可以并行执行。
- 用户触发阶段后应立即获得任务已开始的反馈。
- Agent 生成进度和阶段状态应实时推送到界面。

### 14.6 安全与隐私

- API 密钥不能发送到前端或写入普通日志。
- MiniMax API Key 当前从项目根目录的 `minimax-apikey.txt` 读取；该文件必须加入忽略规则，不得提交到版本库、复制到前端或写入文档。
- 后续部署时应支持通过 `MINIMAX_API_KEY` 环境变量注入密钥，环境变量优先于本地密钥文件。
- 私有角色信息必须由后端过滤。
- 完整提示词和响应可以采用加密存储。
- 应支持按游戏删除全部相关数据。
- 应能够配置 LLM 对话记录的保留时间。

### 14.7 可扩展性

- 角色逻辑应以可注册方式扩展。
- 游戏流程不能依赖固定座位数量。
- 模型调用应通过统一网关封装，避免游戏引擎绑定单一模型提供方。
- 业务层只能依赖项目自定义的 `LLMProvider` 接口，不能直接依赖 MiniMax、OpenAI、Anthropic 等厂商 SDK。
- 模型提供方、模型名称、Endpoint 和能力开关必须通过配置选择，切换模型不应修改 GameEngine、PlayerView、记忆或复盘逻辑。
- 提示词、规则、输出结构和人格均应具有版本号。

## 15. MVP 范围

第一版建议交付以下能力：

1. 单个用户创建和控制游戏。
2. 6 名 Agent 参与。
3. 狼人、预言家、女巫和平民。
4. 完整的夜晚、白天、投票和胜负流程。
5. 用户手动推进阶段。
6. Agent 独立会话、独立身份和私有记忆。
7. 白天依次发言。
8. 投票独立提交并统一公开理由。
9. 保存完整 LLM 请求、响应和结构化结果。
10. 游戏中查看 Agent 对话和记忆。
11. 游戏结束后的全局时间线和单 Agent 复盘。
12. SQLite 本地持久化。
13. 基础错误重试、调用统计和规则测试。

## 16. 当前技术约束与初步方向

当前讨论形成的初步方向如下，最终以技术设计文档为准：

- 前端：Next.js、React、TypeScript。
- 后端：Python、FastAPI、Pydantic。
- 游戏流程：自定义有限状态机。
- LLM 架构：项目自定义 `LLMProvider` 接口和 Provider Registry，业务层不依赖任何厂商 SDK。
- 当前默认 Provider：MiniMax Provider Adapter。
- 当前默认模型：`MiniMax-M3`。
- Agent 调用：Agent Gateway 只调用统一 `LLMProvider.generate()`；MiniMax Adapter 内部使用 `httpx` 调用 MiniMax API。
- API 地址：当前按 M3 官方页面默认使用 `https://api.minimax.io/v1/text/chatcompletion_v2`，同时通过 `MINIMAX_API_URL` 支持 MiniMax 中国区地址或后续兼容接口。
- API Key：开发环境从根目录 `minimax-apikey.txt` 读取，部署环境支持 `MINIMAX_API_KEY`。
- 结构化行动：提示词 JSON 约束 + Pydantic 本地解析和校验，不依赖 M3 服务端 JSON Schema。
- 后续模型切换：通过新增 Provider Adapter 或配置切换完成，不改变游戏领域模型和数据库结构。
- MVP 数据库：SQLite。
- 后续数据库目标：根据并发和部署需求由 SQLite 迁移到 MySQL，不采用 PostgreSQL。
- ORM 和迁移：SQLAlchemy、Alembic。
- 实时更新：REST + SSE。
- MVP 并发：asyncio。
- 复杂断点和长流程需求出现后，再评估 LangGraph。
- AutoGen 已进入维护模式，不纳入新项目候选。
- OpenAI Agents SDK 不纳入当前实现，因为实际模型提供方为 MiniMax。
- 第一版不引入 LangChain、LiteLLM 等额外模型路由框架；如果后续需要大量模型路由、自动降级或统一计费，再通过 `LLMProvider` 接入。

## 17. 待确认事项

以下内容需要在执行计划或开发前进一步确认：

1. MVP 最终采用 6 人局还是直接采用 9 人局。
2. 女巫首夜是否可以自救。
3. 女巫是否允许同一夜同时使用解药和毒药。
4. 狼人击杀意见不一致时如何决定最终目标。
5. 是否允许狼人自刀。
6. 白天发言顺序是固定座位顺序、随机顺序还是从特定座位开始。
7. 平票时是重新发言、重新投票还是无人出局。
8. 死亡玩家是否拥有遗言。
9. 是否采用屠边规则。
10. 用户默认是安全观战还是上帝视角。
11. 是否需要用户登录和多游戏房间。
12. LLM 原始请求和响应默认保存多久。
13. 是否允许从历史节点重新运行并生成一条新的对局分支。
14. 第一版是否需要自动生成 AI 复盘报告。

## 18. MVP 验收标准

当以下条件全部满足时，可以认为 MVP 达到需求目标：

1. 用户能够创建一局游戏并成功随机发放身份。
2. 任意 Agent 的模型输入中不包含规则之外的其他玩家私有信息。
3. 用户能够手动推进一整局游戏直至产生胜方。
4. 所有夜间行动、发言和投票均通过规则引擎校验。
5. 每名存活 Agent 都能进行白天发言并提交带理由的投票。
6. 同一次阶段推进重复请求不会重复结算。
7. 每次 LLM 调用都能查询到实际请求、响应、结构化结果、耗时和 token。
8. 游戏中可以按权限查看指定 Agent 的对话和私有记忆。
9. 游戏结束后可以按时间线回放完整游戏。
10. 复盘中可以切换到单 Agent 视角，查看其当时实际可见的信息和判断变化。
11. 服务重启后，未结束游戏和历史记录不会丢失。
12. 自动化测试覆盖核心状态转换、结算规则和身份隔离。
