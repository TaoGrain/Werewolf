## 故障原因

旧对局 `76370f90-9c21-46cf-baea-a4ae7fb9d1d7` 阻塞在第一天 `DAY_DISCUSSION`，直接原因不是规则引擎，也不是女巫逻辑，而是结构化输出链路不适配推理模型：

1. 每次请求的 `max_tokens` 固定为 800。MiniMax M3 会先生成推理内容，多次在业务 JSON 完成前耗尽额度，产生 `finish_reason=length`。
2. 格式修复提示再次附带完整 JSON Schema。模型在部分修复调用中把 Schema 本身当成回答，返回 `properties/type/required`，没有返回 `speech`、`action` 等业务字段。
3. 白天讨论需要所有存活 Agent 依次成功发言；其中任意一个 Agent 在内部修复后仍失败，整个阶段事务都会回滚。因此外层连续重试 3 次仍停在同一阶段。
4. 配置中已有 `llm_timeout_seconds`，但旧网关没有把它传进实际请求，运行参数与配置不一致。

旧对局共记录 40 次模型调用，其中 27 次结构化输出失败，21 次以 `length` 结束。这组数据确认故障集中在生成预算和 JSON 修复链路，而非死亡结算。

## 修复内容

1. 新增 `LLM_MAX_TOKENS` 配置，默认值设为 2048，并由服务入口和真实运行脚本传入 Agent 网关。
2. 将 `LLM_TIMEOUT_SECONDS` 真正传递到每次 Provider 请求。
3. 修复提示不再重复完整 Schema，只列出所需顶层业务字段，并明确禁止返回 `properties`、`type`、`required`、`title` 等结构定义。
4. 增加自动测试，验证生成上限、超时参数和修复提示都正确传递。
5. 修正复盘页 Token 汇总：优先使用后端 `usage.total_tokens` 权威值，不再把已包含于输出 Token 的 reasoning Token 重复相加。
6. 在 `.env.example` 与 README 中补充真实模型生成预算和超时配置。
