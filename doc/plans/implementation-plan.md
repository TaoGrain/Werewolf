# 多 Agent 狼人杀实施计划

## 1. 文档信息

- 文档状态：实施计划初稿
- 当前版本：0.4
- 更新日期：2026-07-20
- 需求基线：[需求分析](../requirements/requirements-analysis.md)
- 实施目标：完成可本地运行、可完整对局、可检查 Agent 对话、可赛后复盘的 MVP

## 2. 实施原则

1. 游戏规则由确定性代码控制，LLM 只生成玩家发言和行动意图。
2. 身份隔离在后端的数据和上下文构造层实现，不能依靠提示词要求模型“假装不知道”。
3. 每次 MiniMax M3 调用先保存请求快照，再保存响应、解析结果和用量。
4. 游戏事件采用追加式记录，历史事实不被后续操作覆盖。
5. 先完成无 LLM 的纯规则引擎，再接入真实 Agent。
6. MVP 使用 SQLite，数据访问层保持迁移到 MySQL 的能力。
7. MVP 使用自定义有限状态机，不引入 AutoGen 或 LangGraph。
8. 每个里程碑都必须有自动化测试和可演示的验收结果。

## 3. MVP 技术基线

### 3.1 后端

- Python 3.12 或更高版本。
- FastAPI：HTTP API 和 SSE 接口。
- Pydantic：领域 DTO、Agent 输入输出和配置校验。
- SQLAlchemy 2.x：数据库访问。
- Alembic：数据库迁移。
- SQLite：MVP 数据库。
- httpx：由具体 Provider Adapter 调用模型 API；业务层不直接使用。
- Pydantic：定义统一模型请求、响应和 Agent 结构化行动。
- asyncio：并发投票及可并行的 Agent 调用。
- pytest、pytest-asyncio：后端测试。

### 3.2 前端

- Next.js。
- React、TypeScript。
- TanStack Query：服务端状态查询和刷新。
- Zustand：本地界面状态。
- Zod：接口返回数据校验。
- Playwright：端到端测试。

### 3.3 暂不采用

- AutoGen：已进入维护模式，不用于新项目。
- LangGraph：MVP 流程明确，自定义状态机更易审计；复杂断点分支出现后再评估。
- MySQL：MVP 单机阶段暂不引入；后续多房间或并发部署时作为唯一目标数据库。
- PostgreSQL：不在当前或后续技术路线中采用。
- 向量数据库：第一版使用结构化记忆和摘要，不做语义检索。
- Celery、Redis：第一版先使用进程内异步任务；需要可靠后台任务时再引入。
- OpenAI Agents SDK：实际模型为 MiniMax M3，不引入 OpenAI 专属 Agent 运行时。

- 6 人局：2 狼人、1 预言家、1 女巫、2 平民。
- 女巫首夜可以自救。
- 女巫同夜不能同时使用解药和毒药。

- 两名存活狼人先按座位号完成一轮私密交流，交流阶段结束后由主持人再次推进；随后狼人分别秘密提交最终目标，票数最高者成为刀口，平票时在并列目标中使用固定种子随机选择。
- 允许狼人自刀。
- 白天按照存活玩家座位号顺序发言。
- 首轮平票重新投票一次，再次平票则无人出局。
- 被放逐玩家拥有一轮遗言，夜间死亡无遗言。
- 采用狼人数量大于或等于好人数量时狼人获胜的规则。
- 用户默认安全观战，可显式开启上帝视角。

## M4：Agent 接入与身份隔离

### 目标

让每名玩家拥有由应用管理的独立对话历史、人格、私有记忆和严格受限的玩家视图；默认调用 MiniMax M3，但业务逻辑不绑定模型提供方。

### Agent Gateway

实现统一调用入口，职责包括：

1. 根据玩家和阶段构造请求。
2. 在调用前写入 `llm_calls` 和请求快照。
3. 从 Provider Registry 获取当前 `LLMProvider` 并调用统一 `generate()`。
4. 保存请求 ID、响应状态、最终文本、token、推理 token 计数和耗时。
5. 过滤内部推理字段，不将其作为游戏信息展示或传递给其他 Agent。
6. 从模型最终文本中提取 JSON，并使用 Pydantic 校验。
7. 处理超时、限流、敏感内容拒绝、格式错误和有限次数重试。
8. 将验证通过的行动返回游戏引擎。
9. 屏蔽具体模型、鉴权和 API 协议，避免 AgentGateway 和领域层直接依赖 MiniMax。

### 模型 Provider 层

定义项目自有接口：

```python
class LLMProvider(Protocol):
    async def generate(self, request: LLMRequest) -> LLMResponse: ...
    def capabilities(self) -> ModelCapabilities: ...
```

统一类型至少包含：

- `LLMMessage`：统一角色、文本和可选工具消息。
- `LLMRequest`：消息、模型、温度、输出上限、超时和追踪元数据。
- `LLMResponse`：最终文本、工具调用、token、请求 ID、完成原因和安全状态。
- `ModelCapabilities`：流式输出、工具调用、原生结构化输出和多模态能力。

Provider Registry 根据配置解析：

```text
LLM_PROVIDER=minimax
LLM_MODEL=MiniMax-M3
```

业务代码不得导入具体 Adapter。切换模型时只修改配置或增加 Adapter。

### MiniMax Provider Adapter

1. 默认模型 ID 使用 `MiniMax-M3`。
2. 默认请求地址使用 `https://api.minimax.io/v1/text/chatcompletion_v2`。
3. 完整 Endpoint 通过 `MINIMAX_API_URL` 配置，以兼容国际区、中国区及后续 API 调整。
4. API Key 优先读取 `MINIMAX_API_KEY`，未设置时读取 `MINIMAX_API_KEY_FILE`，开发默认文件为根目录 `minimax-apikey.txt`。
5. 请求采用 Bearer 鉴权，密钥不得进入日志、异常文本或数据库快照。
6. 为连接、读取和总调用分别设置超时。
7. 对 429 和可恢复的 5xx 错误执行带抖动的指数退避。
8. 保存供应商响应中的业务审计字段；丢弃 `reasoning_content` 等内部推理文本，仅保存推理 token 数量等用量元数据。
9. 正式开发前运行最小预检；如果兼容 `/v1/chat/completions` 已支持 M3，则优先采用兼容接口，否则使用 M3 官方页面给出的 `/v1/text/chatcompletion_v2`。
10. 将 MiniMax 请求和响应转换为统一 `LLMRequest`、`LLMResponse`，不得让厂商字段泄漏到 AgentGateway。

### Provider 合约测试

1. 所有 Adapter 必须通过同一套请求、响应和异常合约测试。
2. 使用 Fake Provider 验证业务测试不依赖任何真实模型。
3. 验证超时、限流、鉴权失败和敏感内容拒绝能映射为统一异常。
4. 验证缺少某项能力时由 capabilities 明确报告，而不是运行时静默失败。
5. 验证更换 Provider 配置后 GameEngine、数据库和 API 返回结构保持不变。

### 结构化输出策略

1. 提示词要求最终答案只包含一个 JSON 对象，不使用 Markdown 代码块。
2. JSON 字段使用固定英文键，展示内容允许中文。
3. 第一轮解析失败时尝试提取最外层 JSON 对象。
4. 第二轮向同一 Agent 发送只修复格式、不改变决定的修复请求。
5. 仍然失败时记录失败并由阶段重试机制处理。
6. 所有目标存活、角色权限和技能次数仍由 GameEngine 校验。

### 玩家视图

实现 `PlayerViewBuilder`，按阶段生成：

- 公共规则摘要。
- 当前天数和阶段。
- 存活玩家列表。
- 玩家可见的公共事件。
- 本人的角色卡。
- 本角色允许看到的私有事件。
- 本人的私有记忆。
- 当前允许的行动及合法目标。

### 输出结构

分别定义：

- 白天发言输出。
- 白天投票输出。
- 狼人讨论输出。
- 狼人击杀输出。
- 预言家查验输出。
- 女巫行动输出。
- 私有记忆更新输出。

### 提示词任务

1. 编写公共狼人杀规则提示词。
2. 编写角色提示词。
3. 编写不同阶段任务提示词。
4. 编写人格提示词模板。
5. 为所有提示词分配版本号。
6. 明确区分公开发言、公开理由和私有策略摘要。

### 隔离测试

1. 平民视图不包含角色分配表。
2. 预言家视图只包含自己的查验记录。
3. 女巫视图只包含规则允许的刀口和药物状态。
4. 狼人视图只包含狼队友，不包含神职身份。
5. 不同 Agent 的会话 ID 和消息历史完全独立。
6. 公共发言不得自动携带私有上下文元数据。
7. `reasoning_content` 或同类内部推理字段不得出现在公共事件、其他 Agent 上下文或普通观战 API 中。

### 验收条件

- MiniMax M3 能够完成所有基础阶段的合法输出。
- 每次模型调用都能在数据库中查询到完整快照和结果。
- 自动隔离测试中不存在跨玩家私有信息泄漏。
- 无效输出不会直接修改游戏状态。

## M5：游戏 API、任务执行与实时推送

### 目标

提供前端可用的完整游戏控制接口，并实时推送阶段执行状态。

### API 任务

建议实现：

```text
POST /api/games
GET  /api/games
GET  /api/games/{game_id}
POST /api/games/{game_id}/start
POST /api/games/{game_id}/advance
POST /api/games/{game_id}/pause
POST /api/games/{game_id}/retry
GET  /api/games/{game_id}/events
GET  /api/games/{game_id}/stream
GET  /api/games/{game_id}/players/{player_id}/calls
GET  /api/games/{game_id}/players/{player_id}/memory
GET  /api/games/{game_id}/review
```

### 任务执行

1. 阶段推进接口立即返回命令或任务 ID。
2. 后台执行当前阶段。
3. 白天发言按照规则顺序串行调用。
4. 独立投票基于冻结公共状态并行调用。
5. 阶段结束后统一结算。
6. 失败时记录已完成步骤和错误，但不重复执行已结算副作用。

### SSE 事件

至少推送：

- 游戏状态变化。
- 阶段开始和结束。
- Agent 调用开始、完成和失败。
- 新公开发言。
- 投票公开。
- 玩家死亡。
- 游戏结束。

SSE 只能发送当前查看权限允许的内容。

### 验收条件

- API 可以驱动一整局游戏。
- 用户重复点击不会重复结算。
- 页面可以实时收到阶段进度。
- 安全观战接口不会返回身份和夜间秘密。

## M6：基础游戏前端

### 目标

完成用户可操作的游戏界面，支持创建、推进和观察完整对局。

### 页面

1. 游戏列表页。
2. 创建游戏页。
3. 游戏主界面。
4. 游戏错误和恢复界面。

### 游戏主界面

至少展示：

- 当前天数和阶段。
- 玩家座位、存活状态和公开身份状态。
- 公共事件时间线。
- 发言区。
- 已公开投票及理由。
- “开始”“下一步”“暂停”“重试”按钮。
- 当前任务进度和错误状态。
- 安全观战或上帝视角提示。

### 交互规则

1. 阶段运行时禁用重复操作。
2. 收到 SSE 后增量更新页面。
3. SSE 断开后自动重连，并通过 REST 补齐缺失事件。
4. 页面刷新后能够恢复当前对局状态。

### 验收条件

- 用户不通过命令行即可创建并完成一局游戏。
- 刷新页面不会丢失当前进度。
- 阶段失败后能够看到原因并触发重试。

## M7：Agent 检查器与赛后复盘

### 目标

支持游戏中查看 Agent 与 LLM 的实际交互，以及游戏结束后的多视角复盘。

### Agent 检查器

实现以下标签页：

- 时间线。
- LLM 对话可读视图。
- 原始请求和响应 JSON。
- 私有记忆及历史快照。
- 决策和行动。
- token、延迟、模型及错误统计。

### 权限与脱敏

1. 安全观战模式只展示公共数据。
2. 上帝视角展示身份、夜间信息和私有记忆。
3. 游戏结束后解锁完整信息。
4. 服务端根据权限过滤，不能只通过前端隐藏。
5. 私密页面显示明确警告。

### 复盘页面

实现：

1. 全局事件时间线。
2. 夜间和白天事件合并回放。
3. 单 Agent 视角回放。
4. 真实身份和 Agent 怀疑结果对比。
5. 投票命中、跟票、无效行动等基础指标。
6. 每个事件跳转到对应 LLM 调用。
7. 按天数、阶段、玩家和事件类型筛选。

### 复盘约束

- 默认复盘只读取历史事实，不能重新调用 LLM 改写原始记录。
- AI 赛后点评作为后续可选任务，必须与事实记录分开显示。

### 验收条件

- 游戏中可以按权限查看任一 Agent 的模型调用。
- 游戏结束后可以回放所有公开及私有事件。
- 单 Agent 视角只展示其在当时真正可见的信息。
- 任一投票或发言均可追溯到对应模型请求和响应。

- 自动化测试全部通过。
- 至少连续完成多局自动测试对局且无状态损坏。

- 需求分析中的 MVP 验收标准全部满足。

## 7. 核心接口设计顺序

为降低返工，接口应按以下顺序稳定：

1. 领域行动类型和游戏阶段枚举。
2. `GameEngine` 输入输出。
3. `PlayerView`。
4. Agent 结构化输出类型。
5. 持久化实体和 Repository。
6. `AgentGateway`。
7. HTTP API DTO。
8. 前端类型和页面。

前端开发不应早于核心 API DTO 稳定，但可以先使用 Mock 数据开发布局。

## 8. 测试策略

### 8.1 测试分层

| 层级 | 是否调用真实 LLM | 目标 |
|---|---:|---|
| 领域单元测试 | 否 | 验证所有规则和状态转换 |
| Repository 集成测试 | 否 | 验证事务、查询和恢复 |
| Agent 合约测试 | 默认否 | 使用固定模型响应验证解析和隔离 |
| MiniMax M3 冒烟测试 | 是 | 验证 API Key、模型可用性和 JSON 输出约束 |
| API 测试 | 默认否 | 使用 Fake Agent 跑完整流程 |
| 端到端测试 | 可配置 | 验证浏览器中的完整对局 |

### 8.2 Fake Agent

必须优先实现 `FakeAgentGateway`，支持：

- 根据阶段返回固定行动。
- 注入非法 JSON。
- 注入非法目标。
- 注入超时和异常。
- 控制各 Agent 的完成顺序。

这样绝大部分测试不依赖网络、API Key 或模型随机性。

## 9. 数据迁移策略

MVP 使用 SQLite，后续目标数据库为 MySQL。首版需要遵循以下约束，避免迁移时重写业务层：

1. 所有数据库访问经过 Repository。
2. 不在业务代码中拼接 SQLite 专用 SQL。
3. 所有表结构通过 Alembic 管理。
4. ID 使用 UUID，而不是依赖本地自增 ID 作为外部标识。
5. 时间统一保存 UTC。
6. JSON 数据通过 SQLAlchemy JSON 类型封装。
7. 事件顺序使用数据库字段显式保存。
8. 布尔值、时间、JSON、唯一约束和索引均通过 SQLAlchemy 声明，避免依赖 SQLite 隐式类型行为。
9. 字符串字段显式设置长度，索引字段控制长度，确保兼容 MySQL 索引限制。
10. 测试中保持 SQLite 快速测试，同时预留 MySQL 集成测试配置。

触发迁移 MySQL 的条件包括：

- 需要同时运行多个游戏房间。
- 需要多进程或多实例后端。
- SQLite 写锁开始影响 Agent 调用结果入库。
- 需要更强的并发阶段锁和在线备份。
- 准备部署正式的长期运行服务。

## 10. 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| Agent 看到越权身份信息 | 破坏游戏公平性 | 专属 PlayerView、自动隔离测试、服务端权限过滤 |
| 模型输出格式错误 | 阶段无法推进 | 结构化输出、服务端校验、有限重试、用户重试 |
| 阶段重复提交 | 重复用药或重复死亡 | command_id、唯一约束、事务和阶段状态校验 |
| 对话上下文持续增长 | 成本和延迟上升 | 公共摘要、私有记忆快照、上下文窗口预算 |
| 页面实时连接中断 | 用户看不到最新状态 | SSE 重连、事件序号、REST 补偿查询 |
| 模型调用中途失败 | 游戏卡住 | 调用状态持久化、阶段失败状态、可恢复重试 |
| SQLite 并发写入受限 | 写入冲突 | MVP 集中写入；达到条件后迁移 MySQL |
| 复盘内容与真实对局不一致 | 审计失真 | 以不可变事件和调用快照为唯一事实来源 |
| 提示词包含敏感身份并进入普通日志 | 信息泄漏 | 私密日志隔离、默认禁止打印完整模型数据 |

## 11. 完成定义

每个功能只有满足以下条件才能标记完成：

1. 代码实现完成且通过类型和格式检查。
2. 关键路径具有自动化测试。
3. 错误和边界情况有明确处理。
4. 相关数据库变更包含迁移文件。
5. 相关 API 包含请求、响应和错误定义。
6. 不产生未授权的私有信息暴露。
7. 需要用户操作的功能已在前端可完成。
8. 必要文档已同步更新。

## 12. 推荐的首个开发迭代

第一个迭代只聚焦无 LLM 的可运行闭环：

1. 完成 M0 规则确认。
2. 初始化后端工程。
3. 定义角色、阶段和行动类型。
4. 完成发牌和状态机骨架。
5. 实现狼人、预言家、女巫和平民规则。
6. 实现 Fake Agent。
7. 用固定行动跑通一局游戏。
8. 为状态转换、夜间结算和胜负条件补齐测试。

首个迭代完成后再开始数据库和真实模型接入，避免在规则仍不稳定时同时调试 LLM、数据库和前端。
